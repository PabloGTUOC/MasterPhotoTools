### Why

The owner has a new camera, a **Panasonic Lumix LX100** (`DMC-LX100`), which writes `.RW2` files. The
architect tested five of the owner's files on 2026-11-23 (10.9, 14.9 and 34 mm, ISO 400, all portrait):

| | Result |
|---|---|
| rawler 0.7.2 decodes them | **Yes**: 4272×2856, BGGR, black 128, white 4095, the camera's white balance |
| `develop_neutral` | **Works**: 0.41–0.45 s a file, colour and exposure look right |
| `media::raw::is_raw("x.RW2")` | **false**, so Develop refuses the file (`tools/develop.rs:251`) and the folder lists skip it |
| `media::meta::read_meta` | **Empty**: 0×0, no camera, no date, orientation `Normal`. It is not an error, just nothing |
| Orientation in Develop | **Wrong**: rawler reports `Normal` for files the camera marked *Rotate 90 CW*, so portraits come out on their side |
| The camera's distortion correction | **Ignored**: 12.4 px rms from the camera's JPEG at 10.9 mm |

**Why the metadata is empty.** An RW2 is a TIFF whose header has `55 00` where TIFF has `2A 00`
(`II U \0` instead of `II * \0`). nom-exif rejects it. Everything else is ordinary TIFF. With those two
bytes changed **in memory**, the current `read_meta` code reads the camera (`DMC-LX100`), the capture date
(`2026-11-22T11:47:29`) and the orientation (`Rotate90`). The architect checked this on a copy of a real file.

nom-exif needs more than the first IFDs. A patched prefix of 16, 64 or 256 KB gives nothing; 1 MB works.
IFD0 holds the 632 KB embedded JPEG (tag `0x002E`) and nom-exif walks into it. The raw data starts at
IFD0 tag **`0x0118` (RawDataOffset)**, at 636,416 bytes in a 15 MB file. So read **up to RawDataOffset,
not the whole file**: a card of 400 RW2s would otherwise read 6 GB to scan.

**Orientation.** RW2 IFD0 tag `0x0112` (SHORT) holds the EXIF orientation: `6` on these files. rawler does
not read it.

**The camera's distortion correction.** IFD0 tag **`0x0119`** (type 7 UNDEFINED, count 32, stored at the
offset in the entry's value field, from the start of the file) is Panasonic's DistortionInfo: sixteen
little-endian `i16`. ExifTool documents the layout and the equation
`Ru = scale · (Rd + a·Rd³ + b·Rd⁵ + c·Rd⁷)`, but not which values are a, b and c. The architect worked
that out by matching 1,300–4,000 points between Rollchrome's uncorrected neutral and the camera's
embedded JPEG (which the camera has already corrected), and scoring every assignment:

| Model | 10.9 mm | 14.9 mm |
|---|---|---|
| Uncorrected | 12.4 px | — |
| **a = v[8], b = v[4], c = v[11], radius ÷ half-diagonal** | **0.53 px** | **0.75 px** |
| a = v[8], b = v[2], c = v[9] | 0.68 px | 0.75 px |
| a = v[8], b = c = 0 | 1.38 px | 0.76 px |
| best assignment, radius ÷ half-width | 6.55 px | 1.99 px |
| best assignment, radius ÷ half-height | 29.4 px | 6.99 px |

(The errors are measured in the camera's 1920×1280 JPEG. 0.75 px is the matching's noise floor at 14.9 mm.
The free fit lands at a = 0.193 against the stored 0.188.)

The sixteen values `v[0..16]`:

| Index | Meaning |
|---|---|
| 0, 1, 14, 15 | Checksums (below) |
| 2, 9 | Unused here |
| **4** | b = v[4] / 32768 |
| **5** | scale = 1 / (1 + v[5] / 32768) |
| **7** | Correction on when `v[7] & 0x0F == 1` |
| **8** | a = v[8] / 32768 |
| **11** | c = v[11] / 32768 |

**Checksums**, exactly as ExifTool verifies them, with `d` the 32 bytes:

```
checksum(start, n, inc) = fold over i in 0..n: c = (73·c + d[start + i·inc]) mod 0xFFEF, from c = 0
valid ⇔ checksum(4,12,1) ^ u16le(d,2) ^ checksum(16,12,1) ^ u16le(d,28)
        ^ checksum(2,14,2) ^ u16le(d,0) ^ checksum(3,14,2) ^ u16le(d,30) == 0
```

The owner's real tags, both with valid checksums:

| File | 32 bytes |
|---|---|
| 10.9 mm, on | `1b a5 a5 bb 43 01 00 00 0e 07 00 00 b3 01 01 00 1e 18 a9 00 34 00 59 f9 0b 0a 9d 02 19 4a ec 17` |
| 34 mm, off | `93 86 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 34 00 00 00 0b 0a 00 00 29 f3 1d d1` |

The 10.9 mm tag decodes to a = 0.18841552734375, b = 0.05511474609375, c = −0.051971435546875,
scale = 1, on.

**The model in Develop's terms.** The equation maps the **source** (distorted) radius to the corrected one,
so Develop has to invert it, which DV-13's Olympus formula did not need. For each **output** pixel (x, y)
of an image W×H, with centre c = ((W−1)/2, (H−1)/2), v = (x, y) − c, and half-diagonal
R = √(W² + H²)/2:

> ru = |v| / R
> find rd ≥ 0 with scale · (rd + a·rd³ + b·rd⁵ + c·rd⁷) = ru
> the pixel's value is the source **sampled at c + v · (rd / ru)** (bilinear, clamped). At ru = 0 it is c.

W×H is the image `develop_linear` returns (4272×2856 here), in **sensor orientation**. With scale = 1 the
output keeps the centre's magnification and shows a little less at the edges, as the camera's JPEG does.

### What to build

**1. RW2 is a RAW file** (`crates/core`).
- `media/raw.rs`: add `"rw2"` to `RAW_EXTENSIONS`. Rewrite the doc comment above it to say that ORF and RW2
  were added beyond F14's list for the owner's cameras, and that CR3 stays out.
- `tools/f1_dates.rs`: `RAW_EXTENSIONS` becomes `[&str; 7]`, adding `"orf"` and `"rw2"`. ORF is missing
  there too: the date tool has been skipping the owner's XZ-1 files.
- Nothing else. `ingest/scanner.rs` already lists rw2. The Rollchrome callers use `media::raw::RAW_EXTENSIONS`
  (`tools/develop.rs`, `tools/develop_folder.rs`, `rollchrome-desktop/src/commands/develop.rs`) and pick it
  up unchanged.

**2. RW2 metadata** (`crates/core/src/media/meta.rs`).
- A private `fn rw2_metadata_len(head: &[u8], file_len: u64) -> Option<u64>`. `head` is the first bytes of
  a file, at least 64 KB or the whole file if shorter. It returns `None` unless `head[0..4] == b"IIU\0"`.
  Otherwise it reads the IFD0 offset (u32 LE at 4), finds tag `0x0118` (type 4 LONG, count 1) in IFD0 and
  returns `Some(min(value, file_len))` when `value > 8`. It returns `Some(file_len)` when the tag is
  missing or out of range, or when IFD0 cannot be walked inside `head`. Every read is bounds-checked and it
  never panics.
- A private `fn read_rw2_meta(path: &Path) -> Option<MediaMeta>`: `None` if the file is not RW2-shaped.
  Otherwise it reads the first `rw2_metadata_len` bytes (one `File::open`, `take`, `read_to_end`), sets
  bytes 2..4 to `2A 00`, and parses with `MediaSource::from_memory` and `MediaParser::parse_exif`, as
  `read_image_meta_from_memory` does, then `collect_image`. A parse failure gives `MediaMeta::empty()`, as
  for any unreadable file.
- In `read_image_meta`, first: `if let Some(meta) = read_rw2_meta(path) { return meta; }`. Decide by the
  **header bytes, not the extension**: the same header is in `.RWL` (Leica) files.
- Width and height may stay 0 for RW2: the RW2's EXIF does not carry them where `collect_exif` looks. Do
  not add rawler to `meta.rs` to fill them. Note in the Report what `read_meta` returns for them.
- A comment says **why**: the `U` header, the prefix up to RawDataOffset and the 6 GB scan it avoids, and
  that no external program is used (G3).

**3. Orientation in Develop** (`crates/rollchrome-core`).
- New module `media/develop/panasonic.rs`, declared in `media/develop/mod.rs`. Make `frame.rs`'s TIFF
  helpers (`ByteOrder`, `find_tag_entry`, `find_tag_u32`, the read methods) `pub(super)` and use them; do
  not copy them.
- `pub fn rw2_orientation(raw: &[u8]) -> Option<u16>`: `None` unless `raw[0..4] == b"IIU\0"`. Then IFD0
  tag `0x0112`, type 3 SHORT, count 1, value in the entry's value field. `Some(v)` only for 1..=8.
- In `develop_linear` (`media/develop/mod.rs`, where `raw_image.orientation` is turned into
  `orientation`): when `panasonic::rw2_orientation(raw)` is `Some(v)`, use `v`. Otherwise keep what is
  there.

**4. The camera's distortion correction** (`media/develop/panasonic.rs`).
- `#[derive(Debug, Clone, Copy, PartialEq)] pub struct PanasonicDistortion { pub a: f32, pub b: f32, pub c: f32, pub scale: f32, pub on: bool }`
- `pub fn panasonic_distortion(raw: &[u8]) -> Option<PanasonicDistortion>`: `None` unless the header is
  `IIU\0`, IFD0 has `0x0119` with type 7 and count **32**, its 32 bytes are in bounds, **the checksum is
  valid**, and `1 + v[5]/32768 > 0`. Otherwise it returns the decoded values, with `on` set from
  `v[7] & 0x0F == 1`. It returns `Some` even when `on` is false: the camera has said what its lens needs.
- `pub fn undistort_panasonic(linear: &mut LinearProPhoto, d: PanasonicDistortion)`: the model above,
  exactly. Same size out as in, bilinear sampling clamped to the image, rows in parallel with rayon. It does
  nothing when `pixels.len() != width × height`, when `!d.on`, or when a = b = c = 0 and scale = 1.
  - Solve for rd per pixel with **Newton's method**: start at `ru / scale`, at most 8 iterations, stop at
    |step| < 1e-7. Or tabulate f over rd ∈ [0, 1.5] once per image and invert by interpolation. Either is
    fine if the test numbers below hold. If f′(r) = scale · (1 + 3a·r² + 5b·r⁴ + 7c·r⁶) is ≤ 0 anywhere on
    [0, 1.2] (check at 0.01 steps, once per image), do nothing: the model is not invertible, and it is safer
    to leave the picture alone than to fold it.
  - Share the bilinear sampling with DV-13's `undistort` through a private helper in `frame.rs`, not a copy.
    `undistort`'s behaviour and tests stay as they are.
- `frame::apply_camera_geometry`: after the Olympus step, `if let Some(d) = panasonic::panasonic_distortion(raw) { undistort_panasonic(linear, d) }`.
  The three callers (`develop_one`, `DevelopPreview::new_with_lens`, `develop_neutral`) are already in the
  right order, so they do not change.
- `correct_lens` (`media/develop/mod.rs`): lensfun's distortion is also skipped when
  `panasonic::panasonic_distortion(raw).is_some()`, **whether or not `on` is set**. At 34 mm the camera says
  "no correction", and Apple follows the camera. lensfun's vignetting and TCA still apply.

**`crates/core`, three:**
1. `an_rw2_is_a_raw_file` (`tests/raw_tests.rs`): `is_raw` is true for `x.rw2` and `X.RW2`.

3. `an_rw2_is_read_only_up_to_its_raw_data` (unit, in `meta.rs`): a synthetic head `IIU\0` + IFD0 at 8 with
   one entry `0x0118` LONG 1 = 636416 gives `Some(636416)` for file length 15,000,000, and
   `Some(1000)` for file length 1000. The same head with `II*\0` gives `None`. A head cut at 10 bytes gives
   `Some(file_len)` and does not panic.

`every_extension_group_is_recognised` in `f1_dates.rs` covers the two new date extensions on its own, so
no test is needed for them.

**`crates/rollchrome-core`, six** (in `panasonic.rs`; build a synthetic RW2 with a small helper: `IIU\0`,
IFD0 at 8, the entries, then the 32-byte block):
1. `the_panasonic_distortion_is_read`: the 10.9 mm bytes above give a, b, c, scale within 1e-7 and `on`.
2. `a_switched_off_or_damaged_distortion_is_handled`: the 34 mm bytes give `Some` with `on == false`. The
   10.9 mm bytes with byte 16 XOR 1 give `None` (checksum). Count 31 gives `None`. Type 1 gives `None`.
3. `a_file_that_is_not_rw2_has_no_panasonic_geometry`: the same entries behind `II*\0` give `None` from
   both functions. The 10.9 mm file truncated at every length from 0 to its full length never panics.
4. `the_rw2_orientation_is_read`: `0x0112` = 6 gives `Some(6)`. 0 and 9 give `None`. `II*\0` gives `None`.
5. `undistortion_follows_the_panasonic_model`: a 400×300 linear image whose pixel (x, y) is `[x, y, 0]`,
   with the 10.9 mm values (scale 1). Output pixel → (R, G) within **0.01**:
   (0, 0) → (26.112, 19.567); (399, 299) → (372.888, 279.433); (0, 150) → (19.078, 149.952);
   (300, 50) → (294.559, 55.387). The size stays 400×300. With `on: false`, the image is unchanged.
6. `the_distortion_scale_applies`: the same a, b, c with scale = 1 / (1 − 2048/32768) = 1.0666667:
   (0, 0) → (34.947, 26.188); (399, 299) → (364.053, 272.812); (300, 50) → (289.171, 60.721), within 0.01.

### How to work: every step costs money

The build is paid for by the step. These rules are part of the brief:

1. **Run every command in the foreground and wait for it to return.** Never start a command in the
   background and check on it, and never loop or sleep waiting for one. A long build is one step if you
   wait for it.
2. **While working, run only what covers the change:** `cargo check -p phototools-core -p rollchrome-core`,
   `cargo test -p rollchrome-core --lib panasonic`, `cargo test -p rollchrome-core --lib frame`,
   `cargo test -p phototools-core --lib meta` and `cargo test -p phototools-core --test media_tests --test raw_tests`.
3. **Run the full list under Gates once, at the end.** If one gate fails, fix it and re-run that gate,
   not the list.
4. **Read each file once**, using a line range or `grep` for large ones such as `meta.rs` and
   `tools/develop.rs`. Do not re-read a file to confirm an edit you just made.
5. **Do not change approach silently.** If the same failure survives two attempts, stop, say what you
   tried in the Report, and commit what works.
