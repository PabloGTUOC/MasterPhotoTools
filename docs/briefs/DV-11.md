## Brief

### Why

The owner developed an XZ-1 ORF with the look set to **None (neutral)** and found the JPEG muted and
flat, worse than the RAW as the camera or macOS shows it. Measured on the owner's six XZ-1 files
(2026-11-14), against the JPEG the camera embedded in each ORF:

| Averaged over six photographs | Camera's JPEG | Neutral today |
|---|---|---|
| Blacks (2nd percentile of luma) | 0.046 | 0.080 |
| Whites (98th percentile) | 0.601 | 0.575 |
| Contrast (std of luma) | 0.166 | 0.146 |
| Saturation (mean HSV S) | 0.472 | 0.405 |

**The cause.** Neutral uses `tone::base_tone` (DV-1): a straight line of slope 1.25 up to 0.6 and a soft
shoulder. It was designed as the flat base the **built-in looks** were fitted on, which add their own
contrast. DV-7 then offered that base as a finished photograph. Every camera and RAW viewer instead
renders through an S-shaped curve: darker shadows, brighter midtones, and, because the curve is applied
per channel, richer colour.

**The camera's curve was measured.** For each brightness of Rollchrome's linear image, the camera's
output agrees across all six photographs within about ±0.02 (sRGB-encoded), so it is one fixed curve, not
a per-scene adjustment. Pooled over the six, at whole stops, it is the knot table below. Applied per
channel in linear ProPhoto (where `base_tone` is applied today), it gives blacks 0.051, whites 0.599,
contrast 0.164, saturation 0.476, and lowers the mean error against the camera from 0.053 to 0.035.
Applying it to luminance only left saturation 8 % short, so it is per channel.

### What to build

**1. `tone::standard_tone(v: f32) -> f32`** in `crates/rollchrome-core/src/media/develop/tone.rs`.

A cubic Hermite curve through these knots, interpolated in **log2–log2 space**: with `x = log2(v)`,
`y = log2(out)`, and the slope `m` at each knot being `dy/dx` in that space.

| i | v (linear in) | out (linear) | slope m |
|---|---|---|---|
| 0 | 2⁻⁹ = 0.001953125 | 0.00152 | 0.363181 |
| 1 | 2⁻⁸ | 0.00227 | 0.735609 |
| 2 | 2⁻⁷ | 0.00457 | 1.120145 |
| 3 | 2⁻⁶ | 0.01093 | 1.283743 |
| 4 | 2⁻⁵ | 0.02711 | 1.413510 |
| 5 | 2⁻⁴ | 0.07851 | 1.391069 |
| 6 | 2⁻³ | 0.18966 | 1.132482 |
| 7 | 2⁻² | 0.38468 | 0.794696 |
| 8 | 2⁻¹ | 0.60397 | 0.687004 |
| 9 | 2⁰ = 1.0 | 1.0 | 0.765768 |

- Knots are one stop apart, so `h = 1` and, with `t = x − x_i`:
  `y = h00(t)·y_i + h10(t)·m_i + h01(t)·y_{i+1} + h11(t)·m_{i+1}`, where
  `h00 = 2t³−3t²+1`, `h10 = t³−2t²+t`, `h01 = −2t³+3t²`, `h11 = t³−t²`. Return `2^y`.
- **Below the first knot** (`0 < v < 2⁻⁹`): linear through the origin, `v · 0.00152 / 2⁻⁹`.
- `v <= 0` (and NaN) → `0.0`. `v >= 1.0` → `1.0`.
- The slopes are given rather than derived so that the curve is exactly this one; they are the PCHIP
  (Fritsch–Carlson, as in SciPy's `PchipInterpolator`) slopes of the knots, so the curve is monotone.
- Doc comment: what the curve is, that it was fitted to the camera JPEGs embedded in the owner's six
  XZ-1 ORFs on 2026-11-14 by pooling the camera's output per stop, and why it is applied per channel
  (saturation, figures above). Comments explain why, not what (`CLAUDE.md`, House style).

**2. Choosing the curve.** In `crates/rollchrome-core/src/media/develop/mod.rs`:
- `pub enum ToneCurve { Base, Standard }` (`Debug, Clone, Copy, PartialEq, Eq`). `Base` is
  `base_tone`, under the built-in and custom LUT looks; `Standard` is `standard_tone`, for a photograph
  with no look.
- `pub fn linear_to_developed_with(width, height, pixels, orientation, demosaic, tone: ToneCurve)`.
  `linear_to_developed` keeps its signature and calls it with `ToneCurve::Base`, so every existing
  caller and test is unchanged.
- `develop()` is unchanged (`Base`): the look-fitting tool (`examples/fit_looks.rs`) and the looks
  were fitted on it.

**3. Using it.**
- `tools/develop.rs`, `develop_one`: `ResolvedLook::Neutral` develops with `ToneCurve::Standard`;
  `ResolvedLook::Look(_)` keeps `ToneCurve::Base`. Film is untouched (it starts from the linear data).
- `media/develop/preview.rs`, `render_with_data_dir`: `Some(PreviewLook::Neutral)` **and `None`** use
  `Standard` (DV-7 made them the same picture, and they stay the same); `Some(PreviewLook::Look(_))`
  uses `Base`.
- Nothing else changes: not the built-in looks, the LUT files, the film path, Edit, Batch Grade, the
  CLI or MCP surface, the plan format or the front end.

## Report

### What was done

1. **`standard_tone(v: f32) -> f32`** implemented in `crates/rollchrome-core/src/media/develop/tone.rs`:
   - Evaluated using cubic Hermite interpolation in log2–log2 space through the 10 knots at stops $2^{-9}$ through $2^0 = 1.0$ using the Fritsch–Carlson PCHIP slopes.
   - Evaluates linearly through the origin for $0 < v < 2^{-9}$ ($v \cdot 0.00152 / 2^{-9}$).
   - Returns `0.0` for $v \le 0$ and NaN; returns `1.0` for $v \ge 1.0$.
   - Includes doc comment explaining the curve's origin (fitted on 2026-11-14 by pooling camera JPEGs embedded in six XZ-1 ORFs per stop) and why it is applied per channel in linear ProPhoto RGB.
   - Added 4 unit tests in `tone.rs`:
     - `the_standard_tone_passes_through_its_knots` (each knot's output within 1e-5 relative).
     - `the_standard_tone_matches_its_reference_values` (matches SciPy reference values; note on tolerance below).
     - `the_standard_tone_never_decreases_and_is_bounded` (10,000 steps over 0..1.2 monotonic, 0 at 0, 1 at >=1, no NaN, handles negative/NaN).
     - `the_standard_tone_darkens_shadows_and_lifts_midtones_against_the_base` (verifies $S$-curve properties: $standard(0.01) < base(0.01)$ and $standard(0.18) > base(0.18)$).

2. **`ToneCurve` enum and selection** in `crates/rollchrome-core/src/media/develop/mod.rs`:
   - Added `pub enum ToneCurve { Base, Standard }` (`Debug, Clone, Copy, PartialEq, Eq`).
   - Added `pub fn linear_to_developed_with(width, height, pixels, orientation, demosaic, tone: ToneCurve) -> Result<Developed, Error>`.
   - `linear_to_developed` preserved with unchanged signature, delegating to `linear_to_developed_with(..., ToneCurve::Base)`.
   - `develop()` preserved unchanged on `ToneCurve::Base`.

3. **Pipeline integration**:
   - `crates/rollchrome-core/src/tools/develop.rs` (`develop_one`): `ResolvedLook::Neutral` develops with `ToneCurve::Standard`; `ResolvedLook::Look(_)` develops with `ToneCurve::Base`.
   - `crates/rollchrome-core/src/media/develop/preview.rs` (`render_with_data_dir`): `Some(PreviewLook::Neutral)` and `None` use `ToneCurve::Standard`; `Some(PreviewLook::Look(_))` uses `ToneCurve::Base`.

4. **Integration tests**:
   - Updated `neutral_develops_a_photograph_with_no_look_applied` in `crates/rollchrome-core/tests/develop_output_tests.rs` to expect `linear_to_developed_with(..., ToneCurve::Standard)` on `develop_linear(&raw, ...)`'s output.
   - Added `a_look_still_develops_on_the_base_curve` in `crates/rollchrome-core/tests/develop_output_tests.rs`, asserting a built-in look's output bytes match `render(&develop(&raw, ...), Some(&look), JPEG)`.

### Deviations

- **None** from the requested implementation.
- **Reference test tolerance note**: For reference point $v = 0.001$, the brief's table lists expected value `0.000778`. Linear extrapolation below knot 0 yields $0.001 \cdot 0.00152 \cdot 512 = 0.00077824$. Rounded to 6 decimal places, this is $0.000778$, but having only 3 significant figures gives a quantization difference of $(0.00077824 - 0.000778) / 0.000778 \approx 3.08 \times 10^{-4}$. The relative error tolerance was therefore allowed up to $3.5 \times 10^{-4}$ for $v = 0.001$ while all other reference points (which have $\ge 4$ significant figures) match well within $2 \times 10^{-4}$.
