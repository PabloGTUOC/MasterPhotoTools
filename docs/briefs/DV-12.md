## Brief

### Why

The owner compared Rollchrome's neutral JPEG of an XZ-1 ORF with **Photomator's** conversion of the same
file (2026-11-14), and it was not the same. Photomator uses Apple's RAW engine, so `sips` renders exactly
what it does, and the architect measured Rollchrome against Apple's renderings of the owner's six XZ-1
ORFs, a Nikon D610 NEF and the X-Pro2 chart RAF. Four differences, each measured:

| # | Difference | Measured | Cause |
|---|---|---|---|
| 1 | **Framing** | Photomator 3648×2432, Rollchrome 3648×2736 | The XZ-1 was set to 3:2. The ORF records the frame (`AspectFrame` = 0 152 3647 2583) and Apple crops to it; `rawler` does not read it. |
| 2 | **Tone** | Against Apple's renderings, DV-11's curve (fitted to the camera's own JPEG) errs 0.019; a curve fitted to Apple errs 0.015 | Apple's curve has the same midtones but a real black point: much deeper shadows. |
| 3 | **Exposure per make** | Apple renders the D610 **+0.61 EV** and the X-Pro2 **+1.20 EV** brighter than Rollchrome's linear data, the XZ-1 within 0.08 EV | Makes rate their RAW data with different headroom; Apple corrects per make. With that shift alone, the D610 error falls from 0.094 to 0.014. |
| 4 | **Colour (XZ-1)** | Apple's skin is warmer; saturation 0.451 → 0.474 (Apple 0.497) and error 0.015 → 0.014 with a correction matrix | Apple has a tuned profile per camera; Rollchrome uses only the camera's matrix. Measured only on the XZ-1, the one camera with six files. On the D610 and X-Pro2 a matrix gained little (0.0137 → 0.0123, 0.0170 → 0.0170), so only the XZ-1 gets one. |
| 5 | **Detail** | On PB081584 at 100 %, noise reduction 25 leaves face detail 0.92 against the camera's 1.43, and a flat area's noise 0.87 against 2.03 | Develop sets **luminance** noise reduction to the slider's value. Colour noise reduction at 25 removes the blotches (chroma noise 4.60 → 0.27); luminance at 25 erases texture. At luminance 10, noise is 2.08 (the camera's level) and face detail 2.20. |

### What to build

All in `crates/rollchrome-core` (G1). Film simulations and the built-in looks keep their rendering, except
for the frame (item 1), which applies to every look because it is what the photographer framed.

**1. The camera's frame (all looks).** New module `media/develop/frame.rs`:
- `pub fn camera_frame(raw: &[u8]) -> Option<FrameRect>` with `pub struct FrameRect { pub x: u32, pub y: u32, pub width: u32, pub height: u32 }`.
- Reads the **Olympus** aspect frame only; every other file gives `None`. The layout, verified on the owner's
  ORF with `exiftool -v3`:
  1. The file is TIFF (`II`, little-endian; ORF magic is `IIRO` or `IIRS`, so accept any 2-byte magic after
     `II`/`MM` and read IFD0's offset at byte 4).
  2. In IFD0, tag `0x8769` (ExifIFD) gives the Exif IFD's offset from the start of the file.
  3. In the Exif IFD, tag `0x927C` (MakerNote) gives the maker note's offset and length.
  4. The maker note starts with `OLYMPUS\0` then `II` or `MM` (its byte order), then 2 bytes; its IFD starts
     at maker-note offset **12**. **Offsets inside it are relative to the start of the maker note.** Any
     other header (`OLYMP\0`, `OM SYSTEM`, …) gives `None`.
  5. In the maker-note IFD, tag `0x2040` (ImageProcessing; type 13 IFD or type 4 LONG) gives the
     sub-IFD's offset, relative to the maker note.
  6. In that sub-IFD, tag `0x1113` (AspectFrame) is 4 SHORTs: left, top, right, bottom, **inclusive**.
     The value is 8 bytes, so it is stored at an offset (relative to the maker note), not inline.
  7. The frame is `x = left`, `y = top`, `width = right − left + 1`, `height = bottom − top + 1`.
- Every read is bounds-checked; a truncated or odd file gives `None`, never a panic or an error (G10:
  a file without a frame develops as before, which is the correct result, not a swallowed error).
- The coordinates are in the image `develop_linear` returns (after `rawler`'s crop, in sensor
  orientation): on the owner's file, 3648×2736 becomes 3648×2432 at y = 152.
- `pub fn crop_to_frame(linear: &mut LinearProPhoto, frame: FrameRect)`: crops in place. If the frame does
  not fit inside the image, or is the whole image, it does nothing.
- **Where:** after lens correction (DV-9's models are centred on the full sensor), before noise reduction:
  in `develop_one`, in `DevelopPreview::new_with_lens`, and in the new `develop_neutral` (item 6).

**3. Per-make exposure and per-camera colour, neutral only.** New module `media/develop/neutral.rs`:
- `pub struct NeutralCalibration { pub exposure_ev: f32, pub colour: Option<[[f32; 3]; 3]> }`, `Default`
  is 0 EV and no colour.
- `pub fn calibration_for(make: &str, model: &str) -> NeutralCalibration`. Compare case-insensitively;
  `make` **contains** the key (`rawler` reports e.g. `Olympus`, `Nikon`, `Fujifilm`; EXIF says
  `OLYMPUS IMAGING CORP.`, `NIKON CORPORATION`, `FUJIFILM`):

  | Make contains | Model | exposure_ev | colour |
  |---|---|---|---|
  | `olympus` | `XZ-1` (compared without case, spaces or hyphens) | 0.0 | the XZ-1 matrix below |
  | `olympus` | any other | 0.0 | none |
  | `nikon` | any | **+0.6** | none |
  | `fujifilm` | any | **+1.2** | none |
  | anything else | | 0.0 | none |

  XZ-1 matrix (rows sum to 1, so white stays white), applied as `out = M · rgb` on linear ProPhoto:
  ```
  [ 1.20827, -0.16165, -0.04661]
  [ 0.09254,  0.90609,  0.00137]
  [-0.03717,  0.06336,  0.97382]
  ```
  A comment on the table states: each value was fitted to Apple's rendering; Nikon and Fujifilm from
  **one file each** (a D610 NEF, the X-Pro2 chart RAF), so they are provisional until the owner's D60 and
  X100VI files are measured; Fujifilm's dynamic-range modes are not handled.
- `pub fn apply_neutral(pixels: &mut [[f32; 3]], cal: &NeutralCalibration)`: multiplies by `2^exposure_ev`,
  then the matrix if any, then clamps negatives to 0. Parallel with rayon, like the other per-pixel passes.
- The camera comes from `media::lens::lens_info(raw)` (make and model); `None` → `Default`.
- **Where:** for `ResolvedLook::Neutral` only, after capture sharpening, before `ToneCurve::Standard`, in
  `develop_one`. A LUT look and film are untouched. The user's exposure slider still applies as before
  (it is already in the linear data); the calibration adds to it.
- **Preview:** `DevelopPreview` gains a `calibration: NeutralCalibration` field, set in `new_with_lens`
  from `lens_info(raw)`; `from_linear` sets `Default`. In `render_with_data_dir`, the neutral / no-look
  branch applies it to its copy of the pixels before `linear_to_developed_with(…, Standard)`.

**4. Gentler luminance noise reduction.** In `media/develop/mod.rs`, `reduce_noise` sets
`noise_luminance: amount * 0.4` and keeps `noise_colour: amount`. A comment gives the measurement in row 5
above. This changes every look's output, deliberately: it is noise reduction before the look (DV-5).

**5. Preview and output agree.** The preview applies the frame, calibration and noise reduction exactly
as the output does.

**6. `develop_neutral`** (added in DV-11 as the reference the tests use) becomes the whole neutral path for
a RAW with no lens correction, noise reduction or sharpening: `develop_linear` → frame → calibration →
standard curve.

### Tests

Expected names; the count is what matters (see the table).

`frame.rs` unit tests, on a synthetic ORF-shaped TIFF built in the test (a small helper that writes IFD0 →
Exif IFD → Olympus maker note → ImageProcessing IFD with 0x1113):
1. `the_olympus_aspect_frame_is_read` → `FrameRect { x: 0, y: 152, width: 3648, height: 2432 }` for

2. `a_file_without_a_maker_note_has_no_frame` (a plain DNG from `tests/support/dng.rs`, or the helper with
   no maker note).
3. `a_truncated_maker_note_gives_no_frame_without_panicking` (the helper's bytes cut at several lengths).
4. `cropping_to_a_frame_keeps_the_frame_and_ignores_one_that_does_not_fit`.

`neutral.rs` unit tests:

5. `the_xz1_gets_its_colour_and_no_exposure` (`"Olympus"`, `"XZ-1"`; also `"OLYMPUS IMAGING CORP."`, `"XZ1"`).
6. `nikon_and_fujifilm_get_their_exposure` (+0.6, +1.2; no colour).
7. `an_unknown_camera_gets_nothing`.
8. `apply_neutral_keeps_grey_grey_and_scales_by_the_exposure`: a grey pixel stays grey (R = G = B within
   1e-5) through the XZ-1 matrix, and +1 EV doubles it.

`tone.rs`: DV-11's four tests, values updated as above (not new).

`develop_output_tests.rs`:

9. `neutral_applies_the_make_exposure_and_a_look_does_not`: two synthetic DNGs from
   `DngBuilder::new_bayer` with the same pixels, one with `make = "NIKON CORPORATION"` and one with the
   default `"Rollchrome"`. Developed with `NEUTRAL_LOOK`, the Nikon one's centre pixel is brighter in every
   channel. Developed with `builtin:fujifilm-classic-chrome`, the two outputs are byte-identical. Both use
   noise reduction 0, no lens correction, no sharpening.

**Existing tests that may change, and the rule:** noise reduction's new luminance strength can change
DV-5's measured tests (`noise_reduction` in `develop_tests.rs`, `detail_tests.rs`, the desktop preview
tests). If one fails, **report it with its output and do not edit it** in the first pass; the architect
decides. The DV-11 tone tests change by design (item 2).

### How to work: every step costs money

The build is paid for by the step. These rules are part of the brief:

1. **Run every command in the foreground and wait for it to return.** Never start a command in the
   background and check on it, and never loop or sleep waiting for one. A long build is one step if you
   wait for it.
2. **While working, run only what covers the change:** `cargo check -p rollchrome-core`,
   `cargo test -p rollchrome-core --lib frame`, `--lib neutral`, `--lib tone`,
   `cargo test -p rollchrome-core --test develop_output_tests`.
3. **Run the full list under Gates once, at the end.** If one gate fails, fix it and re-run that gate,
   not the list.
4. **Read each file once**, using a line range or `grep` for large ones such as `tools/develop.rs` and
   `preview.rs`. Do not re-read a file to confirm an edit you just made.
5. **Do not change approach silently.** If the same failure survives two attempts, stop, say what you
   tried in the Report, and commit what works.
