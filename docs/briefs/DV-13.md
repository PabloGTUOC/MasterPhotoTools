## Brief

### Why

The owner developed an XZ-1 ORF taken at 6 mm with lens correction **off** and compared it with how macOS shows
the same file (2026-11-15): "there is clearly a change in perspective". It is the lens's barrel distortion.
The architect matched about 5,000 points between Rollchrome's output and Apple's rendering (`sips`, which is
what Photomator uses) and between Rollchrome's output and the camera's own JPEG:

| | Centre | Corners |
|---|---|---|
| Apple's rendering, against Rollchrome's | 1.0 % smaller | 2.7 % larger |
| The camera's JPEG, against Rollchrome's | 1.0 % smaller | 2.7 % larger |

Apple and the camera agree to 0.45 px. They correct the distortion **always**, with numbers the camera writes
into every ORF for the focal length it was set to. Rollchrome ignores them.

Turning Rollchrome's lens correction (DV-9, lensfun's community profile) **on** does not help: at 6 mm it
corrects 6.7 % centre to corner against the camera's 3.8 %, so the picture is bent the other way. The
lensfun maths was checked and is faithful to lensfun; the profile itself disagrees with Olympus.

**The camera's correction, found and verified.** In the ORF's Olympus maker note, ImageProcessing sub-IFD
(`0x2040`), tag **`0x150A`** is 4 `FLOAT`s (TIFF type 11, count 4, 16 bytes): `k1 k2 k3 scale`. On the
owner's files:

| Focal length | `0x150A` |
|---|---|
| 6.0 mm | −0.0534603335 0.0150135821 0.0042942641 1.009765625 |
| 6.5 mm | −0.0390962958 0.0102887880 0.0052287965 1.0048828125 |
| 9.9 mm | −0.0069573941 0.0027793087 0.000973… … |
| 11.8 mm and longer | 0 0 0 0.9912109375 |

The model, fitted against Apple's renderings of four files: the 4:3 and 3:2 frames, at 6, 6.5 and 24 mm.
Every one matched to **0.67–1.41 px rms**. The alternatives err by 8–35 px:

> For each **output** pixel at (x, y) of an image W×H, with centre c = ((W−1)/2, (H−1)/2) and offset
> v = (x, y) − c:
> r = |v| / (√(W² + H²) / 2)   — the **half-diagonal**
> f = scale × (1 + k1·r² + k2·r⁴ + k3·r⁶)
> the pixel's value is the source **sampled at c + v·f** (bilinear).

Three findings that the formula depends on:
- **W×H is the full 4:3 image `develop_linear` returns** (3648×2736 on the XZ-1), **before** DV-12's crop to
  the camera's frame. The correction is applied first, and then the 3:2 frame is cropped.
- `scale` applies **even when k1 = k2 = k3 = 0**. At 24 mm, `0 0 0 0.9912` errs 0.80 px with the scale and
  11.4 px without it.
- The coordinates are in **sensor orientation**, the orientation `develop_linear` returns.

The owner's other cameras need nothing. The X100VI's RAF records Fujifilm's geometric distortion as all
zeros, and the D610's NEF records no coefficients. So this step is **Olympus only**.

### What to build

All in `crates/rollchrome-core` (G1).

**1. Read the tag.** In `media/develop/frame.rs`, which already walks to the ImageProcessing sub-IFD for
the aspect frame (DV-12):
- `#[derive(Debug, Clone, Copy, PartialEq)] pub struct CameraDistortion { pub k: [f32; 3], pub scale: f32 }`
- `pub fn camera_distortion(raw: &[u8]) -> Option<CameraDistortion>`. It follows the same path as
  `camera_frame`: TIFF IFD0 → `0x8769` → `0x927C` maker note with `OLYMPUS\0` header, offsets relative to
  the maker note, IFD at +12 → `0x2040` → **`0x150A`**.
  - Accept the entry only if its type is **11 (FLOAT)** and its count is **4**. Its 16 bytes are stored at
    the offset in the entry's value field, relative to the maker note. Read four `f32` in the maker note's
    byte order.
  - Return `None` when the tag is missing, has the wrong type or count, is truncated, or holds a non-finite
    value, or when `scale` ≤ 0. Return `None` too when **k = [0,0,0] and scale = 1**, because that is no
    correction. **Do not** return `None` for k = 0 with scale ≠ 1, since 24 mm needs that scale.
  - Share the walk with `camera_frame` instead of copying it: a private helper returning the maker-note
    slice, its byte order and the ImageProcessing IFD's offset is enough. `find_tag_u32` reads only the
    value field, so add a sibling that also returns the entry's type and count. `camera_frame`'s
    behaviour and tests do not change.
  - Every read is bounds-checked. A truncated or odd file gives `None`, never a panic (G10). A file without
    the tag develops as before, which is the correct result, not a swallowed error.
- `pub fn undistort(linear: &mut LinearProPhoto, d: CameraDistortion)`. It applies the model above **exactly**,
  with output the same size as input and bilinear sampling clamped to the image. Parallelise rows with
  rayon, the way `media::lens::model::apply` does (`par_chunks_mut`). It does nothing if
  `pixels.len() != width × height`.
- `pub fn apply_camera_geometry(linear: &mut LinearProPhoto, raw: &[u8])`: `undistort` with
  `camera_distortion(raw)` if there is one, **then** `crop_to_frame` with `camera_frame(raw)` if there is one.

**2. Use it in all three places** that now crop to the frame, replacing each
`if let Some(frame) = camera_frame(..) { crop_to_frame(..) }` block with `apply_camera_geometry`:
`develop_one` in `tools/develop.rs`, `DevelopPreview::new_with_lens` in `media/develop/preview.rs`, and
`develop_neutral` in `media/develop/mod.rs`. It applies to **every look**, not only neutral, because it is
the camera's geometry, as the frame is. It does not depend on the lens-correction switch.

**3. No double correction.** In `correct_lens` (`media/develop/mod.rs`): when
`frame::camera_distortion(raw).is_some()`, set the profile's `correction.distortion = None` before calling
`lens::correct`. lensfun's vignetting and TCA still apply. Then `Applied.distortion` is `false` for such a
file. Keep the order in all three places: lens correction (when on), then `apply_camera_geometry`, then
noise reduction.

### Tests

Expected names; the count is what matters (see the table). All are unit tests in `frame.rs`. Extend the
existing synthetic-ORF helper so it can also write `0x150A` (type 11, count 4, 16 bytes at an offset).

1. `the_olympus_distortion_is_read`: the bytes `39 f9 5a bd 87 fb 75 3c e6 b6 8c 3b 00 40 81 3f`
   (little-endian, taken from the owner's 6 mm ORF) give
   `k = [-0.053460333, 0.015013582, 0.0042942641]`, `scale = 1.009765625` (within 1e-7).
2. `a_file_without_the_distortion_tag_has_none`: the helper with only `0x1113`, and a file whose maker note is
   not Olympus.
3. `a_distortion_tag_of_the_wrong_type_or_count_is_ignored`: type 5 (RATIONAL), and type 11 with count 3. Also
   `0 0 0 1.0`, which is no correction, gives `None`, while `0 0 0 0.9912109375` gives `Some`.
4. `a_truncated_distortion_tag_gives_none_without_panicking`: the bytes cut at several lengths.
5. `undistortion_samples_where_the_camera_says`: a 400×300 linear image whose pixel (x, y) is `[x, y, 0]`.
   Bilinear sampling of a linear ramp is exact, so each output pixel holds its source coordinate. With the
   6 mm values above, output pixel → (R, G) within **0.01**:
   (0, 0) → (4.920, 3.687); (399, 299) → (394.080, 295.313); (0, 150) → (3.460, 149.991);
   (300, 50) → (299.416, 50.579). The size stays 400×300.
6. `a_scale_alone_magnifies_evenly`: the same image with `k = 0`, `scale = 0.9912109375`:
   (0, 0) → (1.753, 1.314); (100, 200) → (100.875, 199.556), within 0.01.
7. `the_camera_geometry_corrects_before_it_crops`: the ramp image and a synthetic ORF carrying both the 6 mm
   `0x150A` and an aspect frame `0 50 399 249`. After `apply_camera_geometry` the image is **400×200**.
   Output (0, 0) holds (4.268, 52.129) and output (399, 199) holds (394.732, 246.871), within 0.01, which
   is the full-frame correction then the crop. The other order gives different numbers.

**Existing tests:** none should change. Synthetic DNGs carry no Olympus maker note, so every existing
develop test develops exactly as before. If one fails, **report it with its output and do not edit it**.

### Not in this step

- Fujifilm's and other makes' embedded corrections (`GeometricDistortionParams`, vignetting, CA). The owner's
  X100VI records zero distortion. They wait for a file that needs them.
- Olympus's embedded vignetting or chromatic aberration, and any change to the screen or a new switch.
- The owner's photographs are not in the repository. The architect measures the result on them in review:
  against Apple's rendering, the geometry must match within **1.5 px rms** on the 6 mm, 6.5 mm (4:3) and
  6 mm and 24 mm (3:2) files, with lens correction both off and on.

### How to work: every step costs money

The build is paid for by the step. These rules are part of the brief:

1. **Run every command in the foreground and wait for it to return.** Never start a command in the
   background and check on it, and never loop or sleep waiting for one. A long build is one step if you
   wait for it.
2. **While working, run only what covers the change:** `cargo check -p rollchrome-core` and
   `cargo test -p rollchrome-core --lib frame`.
3. **Run the full list under Gates once, at the end.** If one gate fails, fix it and re-run that gate,
   not the list.
4. **Read each file once**, using a line range or `grep` for large ones such as `tools/develop.rs`. Do not
   re-read a file to confirm an edit you just made.
5. **Do not change approach silently.** If the same failure survives two attempts, stop, say what you
   tried in the Report, and commit what works.

## Report

### What was done
1. **Camera distortion extraction (`media/develop/frame.rs`)**:
   - Defined `CameraDistortion` with `k: [f32; 3]` and `scale: f32`.
   - Factored common Olympus MakerNote traversal into `olympus_image_processing_ifd` and added `find_tag_entry` returning entry type, count, and offset. Added `read_f32` to `ByteOrder`.
   - Implemented `camera_distortion(raw: &[u8]) -> Option<CameraDistortion>` reading tag `0x150A` (type 11 FLOAT, count 4). Validates bounds, finite floats, `scale > 0.0`, and returns `None` for identity (`k == [0, 0, 0]` and `scale == 1.0`) while retaining scale-only transformations (`scale != 1.0`).
2. **Undistortion and camera geometry pipeline (`media/develop/frame.rs`)**:
   - Implemented `undistort(linear: &mut LinearProPhoto, d: CameraDistortion)` using the polynomial model `f = scale * (1 + k1*r^2 + k2*r^4 + k3*r^6)` with half-diagonal normalized radius `r` and bilinear sampling clamped to image bounds. Parallelised rows via rayon `par_chunks_mut`.
   - Implemented `apply_camera_geometry(linear: &mut LinearProPhoto, raw: &[u8])` executing `undistort` first if distortion parameters exist, then `crop_to_frame` if aspect frame exists.
3. **Integration across development paths**:
   - Replaced `crop_to_frame` blocks with `apply_camera_geometry` in `tools/develop.rs` (`develop_one`), `media/develop/preview.rs` (`DevelopPreview::new_with_lens`), and `media/develop/mod.rs` (`develop_neutral`), keeping order: lens correction (when on) -> `apply_camera_geometry` -> noise reduction.
   - Prevented double distortion in `correct_lens` (`media/develop/mod.rs`): clears `profile.correction.distortion = None` when `camera_distortion(raw).is_some()`.
4. **Unit tests (`media/develop/frame.rs`)**:
   - Extended synthetic ORF generator to support both aspect frame and distortion entries with arbitrary types and counts.
   - Added all 7 unit tests: `the_olympus_distortion_is_read`, `a_file_without_the_distortion_tag_has_none`, `a_distortion_tag_of_the_wrong_type_or_count_is_ignored`, `a_truncated_distortion_tag_gives_none_without_panicking`, `undistortion_samples_where_the_camera_says`, `a_scale_alone_magnifies_evenly`, and `the_camera_geometry_corrects_before_it_crops`.
