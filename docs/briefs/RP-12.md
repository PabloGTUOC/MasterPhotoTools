## Brief

### Read first

- `CLAUDE.md` — **Ground rules** (G1–G11), **Gates**.

- `frontend/rollchrome/src/views/Develop.vue`: `triggerPreview`, `executePreview`, `onExposureChange`.

### Goal

Two things from the owner's first use of the real application, and both come first because they stop it being used.

1. **Most of the owner's RAWs are from an Olympus XZ-1, and Develop does not accept `.orf`.** `rawler` has that camera.
2. **Changing exposure in Develop takes seconds per change.** The preview cache is keyed by path **and** exposure, so every exposure is a new read of the RAW (the owner's are often on a NAS) and a whole new demosaic. Exposure is one multiplication in linear light. It must not touch the RAW.

### Change

**`crates/core/src/media/raw.rs`:** `"orf"` joins `RAW_EXTENSIONS`. Leave the separate lists in `tools/f1_dates.rs` and `ingest/scanner.rs` alone.

**`media/develop/preview.rs`:** `DevelopPreview` keeps the **linear** ProPhoto image, developed with exposure 0, upright, reduced to `PREVIEW_MAX_EDGE`, and a second copy reduced to `PREVIEW_DRAFT_EDGE = 800`.

```rust
pub fn new(raw: &[u8], max_edge: u32) -> Result<Self, Error>;
pub fn from_linear(linear: LinearProPhoto, max_edge: u32) -> Result<Self, Error>;
pub fn render(&self, look: Option<&Look>, exposure_ev: f32, draft: bool) -> Result<Rendered, Error>;
```

`render` multiplies by `2^exposure_ev`, then uses **the very same step from linear to `Developed` that `develop` uses**: factor that step out of `develop` if it is inline, without changing what it computes, and do not write a second tone path. **The looks are fitted to the base tone.** Reduce in linear. Then the existing `render` to JPEG quality 90.

**`crates/rollchrome-desktop/src/lib.rs`:** the cache keeps the **eight** most recently used `DevelopPreview`s, keyed by resolved path only, because going back to a photograph should be immediate too. Do not hold the lock while developing; `develop_preview_runs()` stays. A photograph's file having changed on disk is not handled; say so in a comment.

**`commands/develop.rs`, `api.ts`:** `preview_develop` takes `draft: bool`.

**`Develop.vue`:** while the exposure slider is being dragged (`update:model-value`) send `draft: true`; on release (`change`) send `draft: false`. Everything else sends `false`. The one-in-flight rule stays as it is.

**`scripts/check-develop.mjs`:** add, after the fourteen, which stay as they are: *15. During an exposure drag the requests carry `draft: true`, and the release sends one with `draft: false` and the final exposure.*

**`docs/rollchrome/parity-plan.md`:** status line, and say in the RP-12 row that the D60 and X100VI still await a real file. **`docs/rollchrome/manual-verification.md`:** a section `MV-31`: develop real XZ-1, D60 and X100VI files and compare each with the camera's JPEG. `CLAUDE.md`: the counts.

### Do not touch

- `SPECIFICATION.md` (G9). What `develop` computes: **the bytes of a full development must not change**, and every `.cube` stays. `apply_develop`.
- Every existing assertion (G7). The three RP-1 tests that build a `DevelopPreview` from a `Developed`, and the desktop ones that call the old signature, change **only** how they construct it and what they pass; their assertions stay. Remove `from_developed` if nothing needs it.
- No new dependencies (G8).
