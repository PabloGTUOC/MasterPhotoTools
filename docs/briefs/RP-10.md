### Goal

Pick one colour in the photograph and change only that colour: a dress, a car, a sky. The eight HSL bands are too broad for it, and they cannot tell a pale blue from a saturated one. It looks at the pixel alone, so it belongs in the per-pixel pass, and it must cost nothing when it is unused.

### Change

**`crates/rollchrome-core/src/media/edit/point_colour.rs`** (new):

```rust
pub struct PointColour {
    pub hue: f32, pub chroma: f32, pub lightness: f32, // the picked colour, in OkLCh; hue in degrees
    pub range: f32,      // 0..100, default 50
    pub hue_shift: f32, pub saturation: f32, pub luminance: f32, // each -100..100, default 0
}
pub struct CompiledPointColours { /* … */ }
impl CompiledPointColours {
    pub fn compile(points: &[PointColour]) -> Self;
    pub fn is_identity(&self) -> bool;
    /// Oklab in, Oklab out.
    pub fn apply(&self, l: f32, a: f32, b: f32) -> (f32, f32, f32);
}
```

Recipe field `point_colours: Vec<PointColour>`, `serde(default, skip_serializing_if = "Vec::is_empty")`, counted by `is_identity` (a point at rest is identity). Saving more than **eight** is `Error::Refused`.

- *Weight* of a point at a pixel, on the pixel's incoming L, C, h: the product of a hue, a chroma and a lightness weight. Each is `1 − smoothstep(0.5, 1.0, distance / width)`; widths: hue `8 + 0.52 × range` degrees (shortest way round the circle), chroma `0.04 + 0.002 × range`, lightness `0.12 + 0.004 × range`. Multiply by `chroma_fade(C)`, so that neutrals are never touched.
- *Effect*, with every point's weight taken from the **incoming** values and the deltas added, so that the order of the points cannot matter: hue `+ w × hue_shift × 0.3` degrees, chroma `× (1 + w × saturation / 100)`, lightness `+ w × luminance / 100 × 0.3`, clamped. Comment why each constant has its value.
- *Where:* in the existing OkLCh stage of **both** pipelines, immediately **before** the HSL table. With no active point, no conversion happens and the bytes are exactly what they are today. With black & white on, points are skipped: there is no colour left to choose by.

**`PreviewSession::colour_at(x, y) -> Result<PickedColour, Error>`**, the same 5×5 box on the unadjusted settle proxy as `white_balance_at`, sharing its bounds handling, returning `hue`, `chroma`, `lightness`. Chroma below 0.01 is `Error::Refused`: there is no colour there to select. **`crates/rollchrome-desktop`:** the command `colour_at`, `async`, as `white_balance_at` is.

**`api.ts`:** the types, the field and the command.

**`Edit.vue`:** a **Point colour** group in the Colour section, hidden while black & white is on: **Pick a colour**, which uses the eyedropper's mode and mapping with a target (factor them so that both tools share one, changing nothing about `W`); the picked points as swatches; for the selected point, Hue, Saturation, Luminance and Range, and Delete. At eight, Pick is disabled and says why. Commit on release, with one undo step and the label `Point colour`. A refusal is shown and changes nothing. `normaliseRecipe` supplies `[]`.

**`scripts/check-point.mjs`, a harness** (extend the edit harness's stub), `check:point` in `package.json`, each measured in the browser:

## Report

### Summary of changes

1. **`crates/rollchrome-core/src/media/edit/point_colour.rs`** (new):
   - Implemented `PointColour` (hue, chroma, lightness, range default 50.0, hue_shift 0.0, saturation 0.0, luminance 0.0), `PickedColour`, and `CompiledPointColours`.
   - Precomputes widths for hue (`8.0 + 0.52 * range` degrees, shortest circular difference), chroma (`0.04 + 0.002 * range`), and lightness (`0.12 + 0.004 * range`).
   - Weight is calculated as the product of hue, chroma, and lightness falloffs using `1.0 - smoothstep(0.5, 1.0, dist / width)` multiplied by `chroma_fade(c)` to protect near-neutrals.
   - Effects are accumulated into deltas calculated from incoming values so point evaluation order does not matter: hue `+ w * hue_shift * 0.3` degrees, chroma `* (1.0 + w * saturation / 100.0)`, lightness `+ w * luminance / 100.0 * 0.3`.
   - Early exits immediately without arithmetic if incoming chroma is below `CHROMA_FADE_MIN` or if accumulated deltas are zero. Documented the physical and perceptual reason for each constant.

2. **Both pipelines (`crates/rollchrome-core/src/media/edit/pipeline.rs` and `preview.rs`)**:
   - Added `point_colours: Vec<PointColour>` to `AdjustmentRecipe` with `#[serde(default, skip_serializing_if = "Vec::is_empty")]`.
   - Updated `AdjustmentRecipe::is_identity` to check `point_colours.iter().all(|p| p.is_identity())`.
   - Placed compiled point colour evaluation in both pipelines immediately prior to the HSL stage. When black & white is active or when no active points are present, Oklab conversion is completely bypassed, incurring zero cost when unused.

3. **Sampling (`PreviewSession::colour_at`) & Save Guard**:
   - `PreviewSession::colour_at(x, y)` samples a 5×5 box around `(x, y)` on the unadjusted settle linear buffer, sharing bounds checks with `white_balance_at`, and returns `PickedColour { hue, chroma, lightness }`.
   - Samples with `chroma < 0.01` are refused with `Error::Refused("Chroma below 0.01: there is no colour there to select")`.
   - In `crates/rollchrome-core/src/tools/edit.rs`, saving a recipe with more than eight point colours returns `Error::Refused("Cannot save more than 8 point colours")`.

4. **Desktop IPC (`crates/rollchrome-desktop`)**:
   - Added `AppState::colour_at` and `commands::edit::colour_at` exposing async IPC command `colour_at`.
   - Registered `commands::colour_at` in Tauri command handler.

5. **Frontend API & Harness (`frontend/rollchrome`)**:
   - `src/api.ts`: added `PointColour`, `PickedColour` interfaces, `point_colours?: PointColour[]` on `AdjustmentRecipe`, and `colourAt` method on `RollchromeClient`.
   - `scripts/edit-harness/stub-api.ts`: added `colourAtCalls`, `colourAtResult`, `colourAtError`, and implemented `colourAt(sessionId, x, y)`.

6. **UI (`frontend/rollchrome/src/views/Edit.vue`)**:
   - Factored eyedropper mode and coordinates mapping into a shared mechanism with `eyedropperTarget`: `'white-balance' | 'point-colour' | null`. Shortcut `W` toggles white balance without affecting point colour.
   - Added Point Colour panel inside Section 3 (Colour / HSL), hidden while Black & White is active (`v-if="!isBwActive"`), keeping points intact.
   - Provided "Pick a colour" button (`data-testid="point-colour-pick-btn"`), active state highlighting, and disabled state with visible reason when 8 points are reached (`data-testid="point-colour-limit-msg"`).
   - Rendered swatches using native `oklch(lightness chroma hue)` CSS backgrounds.
   - For selected point, rendered Hue (`-100..100°`), Saturation (`-100..100%`), Luminance (`-100..100%`), Range (`0..100`), and Delete point button.
   - Commits history on release with label `Point colour`; undo restores previous state.
   - All controls satisfy minimum 40px touch target requirements.

7. **Browser Verification Script (`frontend/rollchrome/scripts/check-point.mjs`)**:
   - Added `check:point` to `frontend/rollchrome/package.json`.
   - Asserts all 11 requirements from the brief with real Chromium browser interaction and saves layout proof to `frontend/rollchrome/layout-proof/point-colour.png`.

8. **Tests & Documentation**:
